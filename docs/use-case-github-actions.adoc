= Use Case: GitHub Actions CI
:toc:
:toc-placement: preamble

This guide covers using docker-compose-ci as the test backend for GitHub Actions
workflows. The canonical use case is a MediaWiki extension repository that runs its
full test suite on every push and pull request, pinning specific MW/PHP/SMW versions
per matrix row.

IMPORTANT: This guide assumes a minimal `Makefile` exists in the extension repository
that sets the DCI configuration variables and includes `build/Makefile`. This is
described in link:use-case-local-development.adoc#_step_1_set_up_your_makefile[Step 1
of the Local Development guide]. The custom `php-test`, `js-test`, and `dev-test`
targets from that guide are *not* required for GitHub Actions CI — `make ci` is a
DCI built-in target.

== How it works

`make ci` is the single entry point for every CI run. It:

1. Destroys any existing containers and volumes (`make install` → `destroy` → `down -v`).
2. Builds the Docker image without cache — base MW image + all configured dependency
   extensions baked in.
3. Starts the containers and runs `maintenance/install.php` + `maintenance/update.php`.
4. Runs `composer test` (lint + phpcs + phpunit) and `npm run test` (eslint + qunit).

Every run is fully isolated. No state is shared between runs.

`make ci-coverage` works identically but uses the `docker-compose-ci.yml` overlay,
which adds a `./coverage` bind mount so that coverage output is written to
`build/coverage/` on the host. The coverage run uses `composer test-coverage` which
invokes Xdebug; the plain `make ci` run does not.

== GitHub Actions workflow

A typical `ci.yml` runs a matrix of MW/PHP version combinations. The `coverage: true`
flag marks the single row that also generates Clover XML for Codecov.

[source,yaml]
----
name: CI

on:
  push:
  pull_request:

jobs:
  test:
    name: "MW ${{ matrix.mw }} / PHP ${{ matrix.php }}"
    runs-on: ubuntu-latest

    strategy:
      matrix:
        include:
          - mw: "1.39"
            php: "8.1"
            smw: "4.2.0"
          - mw: "1.43"
            php: "8.3"
            smw: "6.0.1"
            coverage: true   # <1>

    steps:
      - uses: actions/checkout@v4
        with:
          submodules: recursive   # <2>

      - name: Run CI
        run: >
          make ci
          MW_VERSION=${{ matrix.mw }}
          PHP_VERSION=${{ matrix.php }}
          SMW_VERSION=${{ matrix.smw }}
        env:
          COMPOSER_AUTH: ${{ secrets.COMPOSER_AUTH }}   # <3>

      - name: Run coverage   # <4>
        if: ${{ matrix.coverage }}
        run: >
          make ci-coverage
          MW_VERSION=${{ matrix.mw }}
          PHP_VERSION=${{ matrix.php }}
          SMW_VERSION=${{ matrix.smw }}

      - name: Upload coverage
        if: ${{ matrix.coverage }}
        uses: codecov/codecov-action@v4
        with:
          files: build/coverage/php/coverage.xml
----
<1> Exactly one matrix row carries `coverage: true`. Use this row's versions for all
    local coverage and phan runs.
<2> `submodules: recursive` clones the `build/` submodule automatically.
<3> Private Composer packages require a token; pass it as a secret.
<4> Coverage re-runs the full suite with Xdebug enabled. Run it as a separate step
    so a coverage failure does not fail the plain CI step.

== Selecting a database

The default database is `sqlite`, which requires no extra service. For mysql or postgres,
set `DB_TYPE` and `DB_IMAGE`:

[source,yaml]
----
- name: Run CI
  run: >
    make ci
    MW_VERSION=${{ matrix.mw }}
    PHP_VERSION=${{ matrix.php }}
    DB_TYPE=mysql
    DB_IMAGE=mysql:8
----

The `docker-compose.yml` includes pre-configured `mysql` and `postgres` service profiles
that are activated automatically when `DB_TYPE` is set.

== Running phan in CI

Phan requires the full MW type graph and runs only on the coverage matrix row to avoid
baseline mismatches across different MW versions. Add it as an explicit step after the
coverage job:

[source,yaml]
----
      - name: Run phan
        if: ${{ matrix.coverage }}
        run: >
          make composer-phan
          MW_VERSION=${{ matrix.mw }}
          PHP_VERSION=${{ matrix.php }}
          SMW_VERSION=${{ matrix.smw }}
----

NOTE: Do not add `phan` to the `composer test` script. It must run as a dedicated step
so that failures are visible before the `|| true` swallow in `composer test-coverage`.

== Browser smoke tests in CI

See link:use-case-local-development.adoc#_browser_smoke_tests_with_playwright[Browser
smoke tests with Playwright] in the Local Development guide for why this exists and
how to write the smoke-test script itself.

`BROWSER_TESTS=true` adds a Playwright + Chromium install (~15 OS packages: X11,
fonts, codecs) to the image build, costing an extra ~1-2 minutes per row that enables
it. Restrict it to a single matrix row — typically the same row that carries
`coverage: true` — rather than enabling it everywhere:

[source,yaml]
----
jobs:
  test:
    strategy:
      matrix:
        include:
          - mw: "1.39"
            php: "8.1"
            smw: "4.2.0"
          - mw: "1.43"
            php: "8.3"
            smw: "6.0.1"
            coverage: true
            browser: true   # <1>

    steps:
      - uses: actions/checkout@v4
        with:
          submodules: recursive

      - name: Run CI
        run: >
          make ci
          MW_VERSION=${{ matrix.mw }}
          PHP_VERSION=${{ matrix.php }}
          SMW_VERSION=${{ matrix.smw }}
          BROWSER_TESTS=${{ matrix.browser }}

      - name: Run browser smoke test   # <2>
        if: ${{ matrix.browser }}
        run: >
          make browser-test
          MW_VERSION=${{ matrix.mw }}
          PHP_VERSION=${{ matrix.php }}
          SMW_VERSION=${{ matrix.smw }}
          BROWSER_TESTS=${{ matrix.browser }}
----
<1> Only one matrix row sets `browser: true`, keeping the Chromium download tax off
    every other row.
<2> `browser-test` is an extension-specific Makefile target (not a DCI built-in) that
    runs the smoke-test script inside the running container, e.g.
    `$(compose-exec-wiki) bash -c "cd $(EXTENSION_FOLDER) && node tests/browser/smoke.js"`.

== Custom extensions in CI

If your extension depends on a third-party extension that DCI does not bundle,
GitHub Actions needs the same `extensions.local.json` mechanism used for local
development — see
link:use-case-local-development.adoc#_installing_non_bundled_extensions_with_extensions_local_json[Installing
non-bundled extensions] in the Local Development guide.

There is nothing CI-specific to configure: `make ci` builds the Docker image the
same way `make install` does, and the Dockerfile's
`COPY extensions.local.json* /tmp/` step picks up the file from the repository
checkout regardless of whether the build runs locally or on a GitHub Actions
runner. The only requirement is that the file is actually present in the checkout
— i.e. *committed*, not just kept locally.

[source,json]
----
// extensions.local.json (committed to the extension repo root)
{
  "extensions": [
    {
      "name": "HeaderTabs",
      "version": "2.4"
    }
  ]
}
----

TIP: If you followed the local development guide and added `extensions.local.json`
to `.gitignore` for local-only experimentation, remove that ignore rule and commit
the file once the dependency becomes required for CI too.

=== Private extensions

If an entry sets `"private": true`, `install-extensions.sh` fetches it via
`get-private-github-extension.sh`, which requires a `GH_API_TOKEN`. Store the
token as a repository secret and pass it through in the CI step. The Makefile hands it to the image
build as a build secret that exists for the installation step only; it is not part of the image.

[source,yaml]
----
- name: Run CI
  run: >
    make ci
    MW_VERSION=${{ matrix.mw }}
    PHP_VERSION=${{ matrix.php }}
  env:
    GH_API_TOKEN: ${{ secrets.GH_API_TOKEN }}
----

=== Composer-based extensions

If an entry sets `composer`, `install-extensions.sh` uses `composer-require.sh`
instead. Private Composer packages need `COMPOSER_AUTH` set the same way as in
the base workflow example above.

== Running phpunit on newer MediaWiki versions

MediaWiki core has been phasing out the `tests/phpunit/phpunit.php` maintenance-script
entry point in favour of running PHPUnit directly via `vendor/bin/phpunit`. Extensions
whose `composer.json` still invoke phpunit the old way

[source,json]
----
"phpunit": "php ../../tests/phpunit/phpunit.php -c phpunit.xml.dist --testdox"
----

will fail once tested against a MW version where that wrapper no longer behaves as
expected. The fix is to invoke `vendor/bin/phpunit` directly, with a small bootstrap
sequence that keeps the script working across the full range of supported MW versions:

[source,json]
----
"scripts": {
  "phpunit": [
    "Composer\\Config::disableProcessTimeout",
    "bash -c 'cd ${MW_INSTALL_PATH:-../..} && { [ -f tests/phpunit/generatePHPUnitConfig.php ] && { php tests/phpunit/generatePHPUnitConfig.php >/dev/null 2>&1 || true; [ -f phpunit.xml ] || printf \"%s\" \"<phpunit><!-- generatePHPUnitConfig --></phpunit>\" > phpunit.xml; } || true; } && MEDIAWIKI_HAS_INTEGRATION_TESTS=1 vendor/bin/phpunit -c extensions/YourExtension/phpunit.xml.dist --bootstrap tests/phpunit/bootstrap.php --testdox'"
  ],
  "phpunit-coverage": "@phpunit --coverage-text --coverage-html extensions/YourExtension/coverage/php --coverage-clover extensions/YourExtension/coverage/php/coverage.xml"
}
----

What each piece does:

`cd ${MW_INSTALL_PATH:-../..}`::
`vendor/bin/phpunit` must be invoked from the MW install root, not from the extension
directory — MW core's own bootstrap files resolve paths relative to it. `MW_INSTALL_PATH`
is set inside the DCI container (see the Dockerfile); the `../..` fallback covers any
other environment where the extension sits two levels below the MW root but the
variable isn't set.

`generatePHPUnitConfig.php` / the `phpunit.xml` fallback::
Newer MW versions read the extension/skin list from a generated root-level `phpunit.xml`
rather than discovering it dynamically. `generatePHPUnitConfig.php` produces that file;
older MW versions don't ship this script at all, so the `[ -f ... ]` guard makes the
whole step a no-op there. If the generator script exists but exits non-zero for any
reason, the fallback writes a minimal placeholder `phpunit.xml` so the subsequent
`vendor/bin/phpunit` call still finds a config file to load.

`MEDIAWIKI_HAS_INTEGRATION_TESTS=1`::
MW core's `tests/phpunit/bootstrap.php` tries to guess, from the PHPUnit invocation,
whether integration tests (which need the full MW settings/service container) are
about to run. The heuristic does not reliably detect that a mixed unit+integration
suite is being invoked directly via `vendor/bin/phpunit` rather than through the
maintenance-script entry point. Setting this variable explicitly on the final
`vendor/bin/phpunit` call is what actually controls the behaviour — skip it only if
the extension's suite is unit-tests-only.

`--bootstrap tests/phpunit/bootstrap.php`::
Passed on the command line so it takes precedence over anything the `phpunit.xml.dist`
file itself declares. If the extension ships its own custom bootstrap file (see below),
point this flag at that file instead of MW core's.

`-c extensions/YourExtension/phpunit.xml.dist`::
The extension's own PHPUnit config, referenced by its path relative to the MW install
root (since the working directory is now the MW root, not the extension directory).

=== Extensions with their own tests/bootstrap.php

Some extensions ship a custom `tests/bootstrap.php` — typically to register a
teardown hook, provide a fallback for a class only available in newer versions of a
dependency, or chain into MW core's bootstrap in some other way. Two MW core bootstrap
files are relevant here and they behave differently:

`tests/phpunit/bootstrap.php`::
The general-purpose entry point. It defines `MW_PHPUNIT_TEST` and, depending on how
PHPUnit was invoked, may also define `MW_PHPUNIT_UNIT` — which switches
`MediaWikiIntegrationTestCase` into a restricted mode without full service-container
access. A test class that isn't itself a `MediaWikiIntegrationTestCase` / doesn't need
that access is unaffected; a test that calls into extension code depending on
`MediaWikiServices::getInstance()` (directly or indirectly) will fail with
`NoSuchServiceException` if this restricted mode is active and the class isn't set up
to request full integration test support.

`tests/phpunit/bootstrap.maintenance.php`::
Used when PHPUnit is invoked through the maintenance-script entry point. It assumes MW
core has already been bootstrapped and `MW_PHPUNIT_TEST` is already defined; if not,
it re-includes `tests/phpunit/phpunit.php` itself — which crashes when PHPUnit itself
(rather than that maintenance script) is the actual process entry point, since that
file expects to own the entire process lifecycle. An extension's custom bootstrap
chaining into `bootstrap.maintenance.php` directly (to reuse its teardown hook, for
example) needs to `define( 'MW_PHPUNIT_TEST', true )` *and* load the full
`tests/phpunit/bootstrap.php` first, so that MW core and the service container are
actually initialized before the teardown hook is registered:

[source,php]
----
// tests/bootstrap.php
$mwTestsDir = ( getenv( 'MW_INSTALL_PATH' ) ?: __DIR__ . '/../../..' ) . '/tests/phpunit';
if ( !defined( 'MEDIAWIKI' ) && is_readable( "$mwTestsDir/bootstrap.php" ) ) {
	require_once "$mwTestsDir/bootstrap.php";
}
if ( is_readable( "$mwTestsDir/bootstrap.maintenance.php" ) ) {
	require_once "$mwTestsDir/bootstrap.maintenance.php";
}
----

When in doubt, prefer pointing `--bootstrap` at MW core's plain `tests/phpunit/bootstrap.php`
directly (skipping the extension's custom file) unless that file provides something the
extension's tests actually rely on — the fewer bootstrap layers involved, the fewer of
these interactions to reason about.

=== Coverage on public repositories only

If a repository is private, do not wire up a `coverage: true` matrix row that uploads
to a third-party service such as Codecov — private source should not leave the
organization's own infrastructure. Restrict the `coverage: true` row and the
`codecov-action` upload step to public repositories; for private repositories, either
omit the coverage row entirely or keep `make ci-coverage` for the local coverage report
without the upload step.

== Updating the DCI submodule in CI

When your `ci.yml` runs on a fresh checkout, the `build/` submodule is pinned to the
commit recorded in your repository. To update to the latest DCI version, run locally:

[source,bash]
----
git submodule update --init --remote
git add build
git commit -m "chore(build): update docker-compose-ci submodule"
----

Then push and let CI pick up the new version.
